### 3. 将持久状态移出 Kernel

v4 中，Kernel 不再读写对话历史，只执行一次 run。App 接管：

- `var/chats` 持久化

- Kernel 运行结果落盘

持久数据从 `data/` 调整为 `var/`，宿主运行态放入 `run/`。

### 4. 收敛 Kernel

Kernel 当前只负责：

- Responses API 请求与流解析
- 单次 run 的内存工作集
- 模型/工具循环
- bash、超时和进程组终止
- guard 策略钩子
- `etc/tools.json` 扩展工具分发
- run/status/stop HTTP API

默认 bash 超时为 30 秒，模型可通过 `timeout_ms` 按任务指定，但不能超过 `bashTimeoutMs` 硬上限。

发行版在 `bin/` 提供 `guard`、`read`、`write`、`edit`；它们可以修改、替换或删除，不被视为不可变的 Kernel 能力。

### 5. 保留 Console 逃生通道

`npm run console` 有两种工作模式：

- App 正常：连接 App API，使用持久对话。
- App 不可用：直接调用 Kernel run API，跨轮历史仅保存在当前 CLI 进程内存。

临时模式已连续运行两轮验证，能够保留当前 CLI 会话上下文，同时不会把持久化重新带回 Kernel。

### 6. 将启动链路移出 Kernel

最初由 `kernel/init.js` 拉起 App。进一步讨论后确认，服务进程编排不应属于 Kernel，因此改为根级 Boot：

```text
npm start
   └── boot.js
       ├── kernel/index.js  :9600
       └── app/server/index.js  :9601
```

当前职责：

- `boot.js`：启动顺序、健康检查、进程监控、退避重启、统一退出。
- `stop.js`：读取 `run/boot.pid`，通知 Boot 停止整套系统。
- Kernel：不启动 App、不监控 App、不写 PID。
- App：作为 Kernel 的 HTTP 客户端和有状态产品层运行。

故障策略已经实际验证：

- App 退出，只重启 App。
- Kernel 退出，结束旧 App 并重启整套系统。
- 重复 `npm start` 会被 `boot.pid` 阻止。
- `npm stop` 会同时关闭 App 和 Kernel，并清理 PID。
- `npm run kernel` 可独立启动 Kernel，不会拉起 App。

相关提交：`0490ab4 refactor(v4): move process supervision to boot`。

## 今日形成的架构结论

1. Kernel 是无持久状态的一次 run 执行引擎，不是产品数据库或服务管理器。
2. App 拥有持久状态、上下文策略、调度和 UI，是默认的有状态 userland。
3. Boot 位于 Kernel 与 App 之外，只处理宿主进程现实。
4. API 是日常协调路径，不是限制 agent 直接访问文件的权限边界。
5. 默认保持开放，根据真实使用中已经发生的问题增加最小修复，不预设复杂限制。
6. 新能力优先通过 `app/`、`bin/`、`etc/tools.json` 和脚本生长；只有不可外包的执行机制才进入 Kernel。
