# 异步调用

Agent 的基本单位是对话。所谓“子 agent”，本质上只是由另一条对话创建并调用的对话。

模型只使用 `bash`。对话之间的操作由上层 HTTP API 提供，不作为模型专用工具。

`POST /api/chats` 只创建用户顶层对话。Agent 派生新对话时必须调用 `POST /api/chats/:当前对话ID/calls`；运行时会将这条路由和归属规则作为固定指令提供给模型。

## 能力

### 创建

一条对话可以创建另一条对话，并立即得到新对话的 ID。创建时写入指令，新对话会自动异步运行。

### 发送

一条对话可以通过自身的 `/calls` 接口并传入 `toChatId` 调用已有执行对话。目标对话空闲时会自动运行；向已经完成过工作的对话再次发起调用，就是继续该对话，不需要单独启动。每次调用都会保存独立的 `calls` 记录。

### 停止

停止指定对话当前正在进行的运行。停止不会删除对话、历史或已经产生的修改。

### 共享上下文

创建对话时，可以从已有对话查询需要的内容，整理成一条上下文消息写入新对话。可以不共享、共享部分或共享全部内容，存储层不区分这些模式。

## 异步调用

一条对话调用另一条对话时：

1. 创建或选择目标对话；新建时将目标对话的 `origin` 设为 `call`。
2. 向目标对话写入 `source=user` 的输入消息。
3. 创建一条 `calls` 记录。
4. 立即返回目标对话 ID 和调用 ID。
5. 目标对话在后台运行。
6. 运行结束后，将结果作为 `source=runtime` 的消息写回发起对话。
7. 更新调用状态，由框架通知 UI 并将结果送入发起对话。

调用状态包括：

- `pending`：等待运行
- `running`：正在运行
- `completed`：正常完成
- `cancelled`：被主动停止
- `failed`：运行失败

## 数据边界

- `chats` 保存对话及基础信息。
- `items` 保存每条对话的 Responses item；执行对话收到的任务为 `source=user`，回传父对话的结果为 `source=runtime`。
- `compactions` 保存上下文压缩结果。
- `calls` 保存对话之间的异步调用关系和状态。

运行进程、权限、订阅连接和 API 行为属于上层，不混入对话内容结构。

AI 直接使用的通信能力只有创建/调用执行对话和停止目标运行。查询可以通过只读 API 或 SQLite 完成；事件订阅和结果回传由框架自动处理。

UI 左侧只显示 `origin = user` 的对话。当前对话创建的 `origin = call` 对话显示在右侧只读面板，点击后可以查看目标对话的完整内容。执行对话中的任务按输入消息显示；回传父对话的结果作为左侧、默认折叠的 Runtime 消息显示，点击后展开正文。
